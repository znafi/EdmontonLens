# EdmontonLens: Tableau data sources and process

This document describes where every field in the Tableau dashboard comes from,
how it is cleaned, how often it refreshes, and what it cannot tell you.
**Live dashboard:** https://public.tableau.com/app/profile/zawad.nafi/viz/EdmontonLens-NeighbourhoodsandTransit/Dashboard1

For the dashboard design see `dashboard_spec.md`; to build it see `BUILD_GUIDE.md`.

**Real vs simulated, in one table**

| Real (City of Edmonton Open Data) | Simulated (generated by the pipeline) |
|---|---|
| Transit routes (243) | Route on-time rate, average delay, delayed trips |
| Transit stops (6,790) and coordinates | `total_trips` (a constant 10, a fallback) |
| Parks (1,043 unique) and areas | Per-stop delay table (not used in the dashboard) |
| Neighbourhood boundaries (399, 2019 vintage) | The on-time part of each neighbourhood's transit score |
| | Waste schedules (source dataset returned HTTP 403, so sample data is used; not in the dashboard) |

## Pipeline

```
data.edmonton.ca (Socrata API) --extract--> pandas transform --load--> BigQuery (edmonton-lens.edmonton_lens)
                                                          \--load--> SQLite (live demo, unchanged)
BigQuery tables --sql/views/*.sql--> 3 views --scripts/export_tableau.py--> tableau/data/*
```

1. `python -m backend.etl.pipeline` extracts, cleans, and loads every table.
2. `python -m scripts.bq_sql views` (re)creates the views; `... checks` runs the quality checks.
3. `python -m scripts.export_tableau` writes the files in `tableau/data/`.

## Files in `data/`

Generated 2026-10-20 (`export_manifest.json` has the exact time and row counts).

### `neighbourhood_scores.csv` / `.geojson`: 399 rows, one per neighbourhood
The GeoJSON has the same fields as properties plus the polygon.

| Field | Meaning | Origin |
|---|---|---|
| `neighbourhood_id`, `neighbourhood_name` | City neighbourhood identifier and name | Real |
| `area_sqkm` | Area computed geodesically (WGS84) from the boundary polygon; the source has no area field | Derived from real |
| `snapshot_date` | Date of the KPI snapshot (latest) | Pipeline |
| `transit_stop_count` | Stops assigned to the neighbourhood | Real stops, derived assignment |
| `park_count`, `total_park_area_sqm` | Parks assigned and their summed area | Real parks, derived assignment |
| `avg_route_on_time_simulated` | City-average simulated on-time rate +/- up to 5 points keyed on the neighbourhood ID | **Simulated** |
| `transit_score` | `clip(stops/4 + on_time*5, 0, 10)` | Real stops + **simulated** on-time |
| `park_score` | `clip(parks*0.8 + park_area_sqm/5000, 0, 10)` | Real |
| `overall_score` | Mean of `transit_score` and `park_score` | Partly **simulated** |
| `overall_rank` | `RANK()` by `overall_score` (ties share a rank) | Derived |
| `stops_per_sqkm`, `park_area_share` | Density measures | Derived from real |
| `overall_score_basis` | Text label for tooltips | n/a |

### `route_performance_daily.csv`: 7,290 rows (243 routes x 30 days)
| Field | Meaning | Origin |
|---|---|---|
| `route_id`, `route_short_name`, `route_long_name`, `route_type` | Route attributes (3 = bus, 0 = LRT) | Real |
| `service_date` | Day (trailing 30 days from the pipeline run date) | Pipeline |
| `on_time_rate` | Share of trips on time, 0.40 to 0.99 | **Simulated** |
| `on_time_rate_7d_avg` | Trailing 7-day mean of `on_time_rate` (window function in the view) | **Simulated** |
| `avg_delay_mins` | Average delay, 0 to 30 min | **Simulated** |
| `total_trips` | Constant 10 for every row (GTFS schedule feed not reachable; fallback value) | **Placeholder** |
| `delayed_trips` | `round(total_trips * (1 - on_time_rate))` | **Simulated** |
| `data_origin` | Always `SIMULATED` | n/a |

## Refresh
- **BigQuery tables: daily, automated.** `.github/workflows/data_refresh.yml` runs at 06:00 UTC and loads BigQuery using a service account (`etl-refresh@edmonton-lens`, roles BigQuery Data Editor + Job User) whose key is the `GCP_SA_KEY` secret. Verified with a manual run on 2026-10-20 (run 39487270413): all tables loaded, row counts unchanged.
- The load is idempotent: re-running on the same day leaves row counts unchanged (verified across four runs, one from CI).
- **Views and Tableau files: manual.** Views read the tables live; `python -m scripts.export_tableau` and re-publishing are needed to refresh the Tableau Public snapshot.
- Tableau Public files are a snapshot; re-export and re-publish to update.
- The BigQuery sandbox expires tables after 60 days (current tables expire about 2026-12-19); re-running the pipeline recreates them.

## Cleaning applied (in `backend/etl/transformers/`)
- Routes: IDs cast to text; non-numeric `route_type` defaults to 3 (bus); duplicates dropped.
- Stops: coordinates coerced to numbers; rows without coordinates dropped; duplicate `stop_id` dropped.
- Parks: the portal returns 1,196 rows for 1,043 unique IDs; duplicates dropped; area coerced to number (missing = 0); amenities normalised to a JSON array.
- Neighbourhoods: Socrata truncates field names to 10 characters (`neighbourh`, `descriptiv`); both forms are accepted. Area derived from geometry.
- Stops and parks get a `neighbourhood_id` by point-in-polygon (Shapely). A point outside every polygon is assigned to the nearest polygon centroid.
- Extraction pages through every Socrata dataset (a single request returns at most 5,000 rows; the stops dataset has 6,790).
- Quality checks (SQL, in BigQuery): null counts, duplicate keys, orphan references, coordinate bounding box, freshness.

## Known limitations
1. **Delays and on-time rates are simulated.** They come from a fixed-seed random model and say nothing about real ETS performance. Never cite them as findings.
2. **Scores saturate.** 278 of 399 neighbourhoods have a park score of 10; 71 tie at an overall score of 10. The scores order neighbourhoods poorly at the top end. The formulas are ad hoc, not a published index.
3. **Industrial and edge areas are included** (e.g. "Anthony Henday ..." ring-road areas, industrial districts) and show 0 parks.
4. **1,012 stops (15%) lie outside the polygon they are assigned to** (nearest-centroid fallback). The quality check reports this as a WARN. Stop counts for neighbourhoods near these stops are approximate.
5. **Boundaries are the 2019 vintage** and may not match current neighbourhoods.
6. `total_trips` is a placeholder and `waste_schedules` is sample data; neither should be used.
7. The BigQuery project is on the free sandbox (60-day table expiry, no DML). Local runs use a personal Google login (Application Default Credentials); CI uses the service account.
8. The published workbook (https://public.tableau.com/app/profile/zawad.nafi/viz/EdmontonLens-NeighbourhoodsandTransit/Dashboard1) implements the four sheets, the dashboard and the Transit-Park Quadrant calculated field, but not yet the other calculated fields, the parameter and the filters in `dashboard_spec.md`. It is embedded in the web app at https://edmonton-lens.vercel.app/dashboard.
